# 원본 대비 역설계 검증 보고서

| 항목 | 내용 |
|---|---|
| 검증일 | 2026-10-19 |
| 원본 | http://110.10.147.54:5173 (기관 자산·서비스 관리) |
| 대상 | BingoASM (본 저장소) |
| 백엔드 | Java 17 + Spring Boot 3 (2026-10-19 Node.js에서 전환, 아래 7장 재검증) |
| 결론 | 원본의 화면 12종, API 42종, 데이터 형식, 서비스 처리 흐름, 통계 산식을 모두 구현했습니다. 원본에 있는 응답 필드는 전부 들어 있고, 통계 값은 같은 데이터에서 4개 집계 단위 모두 일치합니다. |

## 1. 검증 방법

1. **원본 소스 대조**: 원본이 Vite 개발 서버로 운영되어 `?raw` 요청으로 원본 소스 28개 파일(약 3,700줄)을 받을 수 있었습니다. 화면 12종을 한 줄씩 읽고 차이를 목록으로 만들었습니다.
2. **API 형식 비교**: 같은 엔드포인트 20개를 원본과 BingoASM에 동시에 호출하고, 배열 안의 선택 필드까지 합친 응답 구조를 자동으로 비교했습니다. 원본 호출은 원본 로그인 화면에 공개된 데모 계정으로 읽기 요청만 했습니다.
3. **통계 값 비교**: 시드 데이터를 원본과 같게 맞춘 뒤 일간·주간·월간·연간과 유형 필터 조건에서 통계 응답을 키 순서·동점 정렬과 무관하게 비교했습니다.
4. **기능 테스트**: 요청자·접수자·처리자·관리자 4개 계정으로 요청부터 종결·만족도까지 전체 흐름, 권한 거부, 자산 hw/sw 저장, 필터를 API로 실행했습니다.
5. **화면 테스트**: 브라우저에서 화면 14개 경로의 핵심 요소, 브레드크럼, 탭 선택, 도면 클릭 배치를 확인했습니다. 라이트·다크 모드에서 텍스트 요소 1,145개의 명도 대비를 측정했습니다.

## 5. 확인할 수 없었던 부분

| 항목 | 상황 | BingoASM의 처리 |
|---|---|---|
| 원본 백엔드 내부 로직 | 서버 코드는 비공개 | API 응답과 화면 동작으로 역추론 |
| 역할별 권한 목록 | 관리자 외 역할의 권한 목록은 응답으로 확인 불가 | 화면 권한 검사와 역할 설명을 근거로 정의 (`server/src/main/java/com/bingoasm/auth/Roles.java`) |
| 변경 API의 서버 규칙 | 원본 데이터를 바꾸지 않기 위해 원본에는 쓰기 요청을 보내지 않음 | 원본 화면 코드가 보내는 요청 형식에 맞춰 구현하고, BingoASM에서 쓰기 동작을 테스트 |
| 계정 잠금 횟수 | 원본에 반복 실패를 시도하지 않음 | 5회로 설정 (`loginFailCnt` 필드는 원본에 존재) |
| 도면 크기 정보 | 원본 응답의 planWidth/planHeight는 항상 0 | 필드만 유지 |

## 6. 재검증 방법

원본과 BingoASM을 함께 띄운 상태에서 아래 순서로 다시 확인할 수 있습니다.

1. `npm run reset-db` 후 API 서버를 다시 시작해 원본과 같은 시드로 맞춥니다.
2. 같은 계정으로 두 서버에 로그인해 위 엔드포인트의 응답 구조를 비교합니다.
3. `/api/stats/services?period=MONTH&fromDate=2026-01-01&toDate=2026-10-19`처럼 기간을 고정해 통계 값을 비교합니다. `fromDate`를 비우면 오늘 기준 기본 기간이 쓰이므로 날짜를 고정해야 합니다.

### 8.1 검증 중 찾아 고친 것

| 문제 | 수정 |
|---|---|
| 이관·취소 뒤 컨트롤러가 처리자 입장의 상세를 다시 읽어 404 | 취소·삭제는 빈 응답, 이관은 `{transferred:true}` 결과 반환 |
| 기사가 비밀글에 답변하면 저장된 뒤 403 | 답변 전에 비밀글 열람 권한 검사 |
| 실 상세에 자산 목록이 없음 | `assets` 배열 추가 |
| 실 영역 rect가 0~1로 잘려 저장 | 자산 핀과 같은 퍼센트(0~100)로 통일 |
| 분류 기본 내용연수가 자산 응답에 비어 있음 | 자산 생성 시 분류 기본값 적용, 응답은 유효 내용연수 |
| 로그인 이력의 IPv6 주소가 마스킹되지 않음 | `2001:db8:****` 형식으로 마스킹 |
| 학교 사용자가 다른 학교 무선장비를 조회하면 자기 학교 목록으로 조용히 대체 | 다른 학교 지정 시 403으로 통일 |
| **이메일·휴대폰이 평문으로 저장됨** — `CryptoConverter`의 키가 Spring 생성자에서만 설정되는데 Hibernate 6가 컨버터를 자체(no-arg)로 만들어 키가 비어 있었고, 키가 없으면 평문을 그대로 저장하도록 되어 있었음 (DB를 직접 조회해 발견) | 키를 정적 초기화(`DATA_KEY` 환경변수 → 기본값)로 항상 준비하고 `CryptoKeyInit` 빈이 `app.data-key`를 덮어씀. 키 없이 저장하는 경로 제거. 기동 시 `PiiMigration`이 평문으로 남은 행을 찾아 암호화(네이티브 SQL). H2·PostgreSQL 모두 DB를 직접 열어 `enc:` 암호문만 남은 것을 확인 |

### 8.2 PostgreSQL 제자리 업그레이드

4일 전부터 쓰던 PostgreSQL 16 DB(기존 BingoASM 데이터 13개 테이블)에 `postgres` 프로필로 새 서버를 올렸습니다.

| 검증 | 결과 |
|---|---|
| 스키마 | 오류 없이 테이블 31개(18개 추가), 기존 테이블에 컬럼 추가 |
| 데모 데이터 | 학교가 없어 `AsDataSeeder` 실행: 학교 8, 업체 4, AS 신청 20 — 기존 자산·서비스 요청 데이터 유지 |
| 동작 | school01 로그인, AS 요약, 봉황초 실 8개, 자산 QR PNG 정상 |
| 암호화 | 처음 올렸을 때는 평문이 저장되어 있었음(위 8.1 참고). 수정 후 재기동하니 `PiiMigration`이 기존 12행을 암호화했고 `users.email/mobile`이 모두 `enc:` 암호문(평문 0행), API는 복호화된 값을 돌려줌 |

### 8.3 확인하지 못한 것

- 화면: 원클릭 AS 모듈은 API까지이며, 동료 UI 클론이나 BingoASM React 화면에 아직 연결되지 않았습니다(연결 순서는 `FRONTEND_GUIDE.md` 3절).
- OTP 실제 발송(메신저·SMS)과 cbe.go.kr의 실제 처리 보고서 PDF 양식은 원본 사이트의 비공개 부분이라 구조만 맞췄습니다.
